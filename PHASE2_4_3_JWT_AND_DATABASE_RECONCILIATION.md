## 2. JWT Issuer Transition & Expiration Formalization

### 2.1 Formal Assumptions of the 7-Day Window
The claim that all legacy tokens expire after 7 days requires the following five formal engineering conditions to be strictly satisfied:

1. **Condition 1 (Universal Issuer Upgrade at $T_0$):**  
   Express is the **sole system** authorized to issue authentication tokens. At timestamp $T_0$, the updated code deploying `generateToken()` strictly mandates `iss: 'stroom-api'` and `aud: 'stroom-client'`. Legacy issuance stops completely and permanently across all running instances.
2. **Condition 2 (Maximum Token Lifetime Bound):**  
   All tokens generated by Express prior to $T_0$ were created with `{ expiresIn: '7d' }`. No token was ever created with a lifetime exceeding $604,800\text{ seconds}$ ($7\times 86400$).
3. **Condition 3 (Clock Synchronization Bound):**  
   NTP clock synchronization across Cloudflare edge data centers and the Express origin host operates within a strict bound of $\pm 60\text{ seconds}$ ($|\Delta t| \le 60\text{s}$).
4. **Condition 4 (Immutable Payload):**  
   JWTs are tamper-proof via HMAC-SHA256 signature; client-side tampering of `exp` causes cryptographic signature validation failure.
5. **Condition 5 (Strict Cutover Deadline):**  
   The legacy token acceptance window closes at exactly:
   $$\text{Cutoff Timestamp} = T_0 + 604,800\text{ seconds} + 60\text{ seconds (leeway)} = T_0 + 604,860\text{ seconds}$$

### 2.2 Rejection Policy Upon Cutoff
At $T_0 + 604,860\text{s}$:
- Any token lacking `iss: 'stroom-api'` or `aud: 'stroom-client'` is rejected immediately with:
  ```json
  {
    "error": "Invalid token issuer or audience. Please log in again.",
    "code": "TOKEN_ISSUER_REJECTED"
  }
  ```
- This rejection applies even if the token's cryptographic signature matches `JWT_SECRET`.
